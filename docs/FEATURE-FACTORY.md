# The Feature Factory

Entry: `/app/projects/feature-factory/play`. The root project URL opens the same dedicated entrance. The Projects gallery card goes directly into the new simulation. Existing legacy chapter/run URLs are preserved.

## The experience

Ignis is a fictional team-workspace company with a weekly release ritual. The player owns Core Platform: a roadmap proposal, a daily attention budget, and Friday’s go/no-go call. The violet-and-brass factory floor and giant gong give this level its own identity. The working middle is a PM desktop, rather than a sequence of cutscenes.

The opening introduces the gong, asks which metric gets the wheel, then introduces Reva, Cass, Nils, Kofi, Amara and Lila. The player answers Cass in their own framing. Monday opens the planning board: select tickets, divide a fixed 100% of engineering effort among Build, Harden and Quality, write a sprint goal, and leave a reason. The authored backlog contains all 12 handoff items. True effort is seeded per ticket and revealed only after shipment.

The quarter is three five-day sprints. Each day starts with six attention points and three to five state-selected inbox items. Reading and replying each cost one point; asks cost one, meetings two, QA two, a customer call two, unblocking one, and a ten-second stress test one. Opening a previously read message is free. Planning changes are free before commitment; later scope changes cost attention. Engineering progress advances exactly once when the player closes the day. Ignored messages age, reduce the sender’s trust, then expire; the recap names these costs.

The desktop contains Inbox, Board, Dashboard and Day panels. Desktop tabs focus and scroll to their panel; phones show a single tab at a time. Board progress is generated by the day’s allocation and capacity; dragging cannot pretend work is finished. Both drag and button controls change scope. The allocation triangle supports pointer manipulation, with equivalent native keyboard sliders that keep the total exact.

Pulse counts sessions and responds to demo features. Its optional Three.js ring uses actual Pulse values. The Truth tab costs one initial attention point and reveals returning-user instrumentation; it reduces incident data fog. The D30 figure is explicitly a simulated projection across fifteen workdays, not an observed thirty-day experiment.

All six people have eight ask topics. Answers draw from the actual plan, debt, bugs, evidence, trust, memories and player-authored reasons. Low trust limits depth; high trust reveals additional warnings. There are 120 caption-matched, offline-produced synthetic recordings for authored dialogue, event leads and ask introductions. Generated data and exact player quotes appear as clearly labelled typed follow-ups, rather than being presented as audio that was never recorded. Captions and manual continuation remain usable without audio. Portraits have five static expressions and no mouth animation.

Friday protects one attention point for the release call. The player selects criteria and links matching evidence. Missing, failed or stale evidence cannot prove an enforced criterion. Hold remains available. Go, limited rollout, Hold and Cut have different costs; unfinished cards never ship, and Cut keeps only completed low-debt changes. A gong or deliberate silence precedes a causal recap. Evidence strength measures coverage, not candidate skill.

An incident requires three relevant log lines and a response. Wrong marks consume attention while preserving two recovery points. Truth instrumentation removes noise. The incident identifies its originating record, and the response quotes the original reason rather than substituting the recovery decision. Rollback, patch and flag-off are available where valid. Incidents discovered on the final day can remain unresolved in the review; the model does not invent a recovery after the quarter ends.

The Zenith review asks for three authored slides: Headline, Evidence and Ask. The audience reacts to each slide using actual results; spin earns short-lived applause and a later request for substantiation. The final review shows outcomes, descriptive archetypes, decision receipts, reflection and export. Two alternative policies are re-simulated through the same daily reducer with the original seed. The work yields between actions so the UI remains responsive. These are illustrative policy comparisons, not claims of causal certainty about a real company.

## Content and determinism

- 23 screen definitions, 42 distinct conditional events, 48 ask topics, 12 backlog tickets and 120 recordings.
- Event files load when the corresponding sprint begins. Each contains the complete conditional deck with its sprint window; the engine filters state predicates and cooldowns, then draws a seeded three-to-five-item morning.
- Fixed authored first-sprint anchors include the customer-loss message, retention prompt, Wednesday SSO ask and Thursday autosave P1, subject to their stated conditions.
- The world reducer uses saved mulberry32 state and daily steps. No time-of-day, network service or wall-clock RNG affects simulation outcomes. UI stress playback lasts ten real seconds, pauses when hidden and records a seeded load result.
- Player text is stored verbatim up to the stated character limit. It is quoted in inbox follow-ups, character memories, incident records, recaps, slides and review. Prose is not scored by keywords.
- The handoff names Day 0 Monday followed by Day 1 Tuesday while requesting fifteen workdays. This implementation consistently uses Days 1–15, Monday–Friday, with the opening gong taking place the preceding Friday.
- Placeholder balancing values remain authored simulation rules. Human playtests and expert review remain pending.

## Safety and integration

The two exact entry routes bypass workspace profile gates and remove workspace chrome. Their client implementation is dynamically imported with a stable loading screen. Styles are scoped. No account schema, authentication provider, global theme or existing project save is changed.

The namespace is `pmforge.feature-factory.v1`. Each save uses a checksum envelope, pending write, last-good backup and latest-run pointer. Storage failures leave the run playable and encourage export. Saves remain local and do not sync to an account. Checksums detect accidental corruption; they are not encryption or anti-cheat controls.

`PMFORGE_FEATURE_FACTORY_ENABLED=false` followed by a server restart closes both new entry routes while retaining saved quarters. Route-level and screen-level error boundaries offer recovery and exit. The immutable preview launcher continues to pin a complete production build, so rebuilding does not mix navigation assets with the running preview.

The Pulse renderer loads only with the level and when visible. It renders a data-driven frame rather than running a permanent graphics loop. Geometry, materials, context and observers are disposed on exit. An SVG ring and DOM numeric values provide fallback parity. Reduced motion removes decorative animation. Audio instances release their source and listeners; hidden tabs pause audio and stress playback. The gong is finite, with no strobe or rapid flashes.

Developer hooks are opt-in through `?qa=1`, retained only for that tab via `pmforge.feature-factory.qa` session storage. They expose `setSeed`, `advanceDay`, `choose`, `state` and `runCounterfactual` while the level is mounted, and are removed on exit. They are not used for normal progression.

## Validation

The verified production preview passes 185 unit tests across the product and all project suites, 30 deterministic strategy runs, 89 full-flow browser checks, 25 resource/fallback checks, 12 incident/audio checks and 18 shared navigation checks. All 315 checked routes and 190 assets return 200. Lighthouse accessibility scores 100 on the entrance. Twenty soft entries dispose all twenty GPU contexts; global listener counts remain 173 before and after. The runtime rollback switch closes both entry URLs and preserves saves. Exact build, reports and limitations are collected in `feature-factory-verification/summary.json`.

`npm run test:feature-factory` runs the engine tests and ten strategy paths over three seeds, replaying each for exact determinism. They include Pulse-first, foundations, balanced flags, ignoring Nils, never opening Truth, retention steering, no release criteria, holding all releases, accepting scope, and spinning the review.

`scripts/check-feature-factory.ts` runs before every build and in CI. It validates the screen manifest, event conditions, choices, feature references, speaker/expression IDs, all ask topics, template slots, word limits and caption/audio parity. It also checks generated state references and terminates both counterfactuals.

Browser evidence and exact result counts live in `docs/feature-factory-verification`. Desktop Chromium and mobile viewport emulation are covered. Physical Safari/iOS, Firefox, mid-range Android GPUs, professional screen-reader testing, subjective acting review and human think-aloud sessions are not certified by this desktop pass.

## Provenance

Subframe MCP inspiration searches covered industrial dashboards, Kanban movement and fixed-budget allocation. [Status transfer](https://www.subframe.com/motion/status-board) and [A budget that stays balanced](https://www.subframe.com/motion/locked-budget-balance) informed spatial feedback and the exact-total allocation interaction. The latter’s motion metadata and source were inspected; no example source was copied and no Subframe project was edited.

All SVG factory and character artwork, controls, Three.js arrangement and soundscapes are original code assets. Kokoro-82M v1.0 recordings are prerecorded synthetic speech; emotion labels adjust pacing rather than providing native acted emotion. Credits and licence ship with the audio. The offline model and Python production tools remain in ignored local tooling and outside deployment traces.
